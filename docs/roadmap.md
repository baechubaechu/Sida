# 로드맵

Sida가 어디로 가는지와 그 순서를 적는 문서입니다. 방향과 단계는 여기에 두고, 개별 작업과 진행 상태는 GitHub Issues에 둡니다. 방향이 바뀌면 이 문서를 PR로 고칩니다.

마지막 갱신: 2026-10-06

## 지금 상태

- CLI로 동작합니다. 허브에서 프로젝트를 고르고, Conductor와 대화하며 전문가 12개를 필요할 때 실행합니다.
- 실행 모드는 클라우드(OpenRouter)와 로컬(Ollama) 중에서 고릅니다. PC별 설정은 `config.local.yaml`에 있습니다.
- 법령 검색은 법제처(law.go.kr)의 지능형 검색을 직접 호출합니다. 기본으로 꺼져 있고, 켜려면 법제처 인증값만 있으면 됩니다.
- `/site <주소>`로 필지, 용도지역, 건폐율·용적률의 법정 범위와 지자체 조례값을 가져옵니다.
- 코드는 `sida/` 패키지이고, 전문가 영역별 코드는 `sida/experts/<영역>/`에 있습니다.
- 사용 대상인 건축 설계자와 학생에게 터미널은 진입 장벽입니다. 이것이 다음 단계의 이유입니다.

### 1. 코어와 화면 분리 — 완료 (#11)

웹 UI를 붙이기 전에, 대화와 실행 로직이 터미널 입출력에 묶여 있는 부분을 풀어냅니다. 이 단계에서는 사용자에게 보이는 변화가 없어야 합니다.

- `session.py`의 Conductor 턴, 전문가 실행, state 갱신 제안과 적용을 `print`/`input` 없이 값을 주고받는 함수로 분리합니다.
- 진행 상황(전문가 실행 중, RAG 검색 중, 경고)은 출력 대신 이벤트로 전달합니다.
- `fail()`이 프로그램을 종료시키는 대신 예외를 던지게 하고, 종료는 CLI 진입점에서만 합니다.
- CLI(`chat.py`, `run.py`)는 분리된 함수를 그대로 써서 지금과 똑같이 동작합니다. 기존 테스트가 그대로 통과하는 것이 완료 기준입니다.

### 2. 웹 UI 첫 버전 — 진행 중

네 부분으로 나눠 진행합니다.

| 부분 | 코어·JSON API | 화면 |
|---|---|---|
| ① 서버 뼈대와 프로젝트 허브 | 완료 (#12) | 완료 (#12) |
| ② 세션 화면 (대화, 전문가 실행) | 남음 | 남음 |
| ③ state 갱신 승인, 브리프·state 편집 | 완료 (#18) | 남음 |
| ④ 설정 화면 | 남음 | 남음 |

역할 분담(2026-10-04): 웹 화면은 팀원이 진행합니다. ③의 승인·건너뛰기, 오래된 승인안 거절, 버전 확인과 백업을 포함한 문서 편집 코어·JSON API·테스트를 준비하고, 화면 연결은 팀원이 진행합니다. 함수와 API 명세는 [state-editing.md](state-editing.md)를 참고하세요.

로컬에서 실행하는 웹 UI입니다. `run.bat`을 실행하면 브라우저가 열립니다. 서버에 올리는 서비스가 아닙니다.

- 프로젝트 허브: 목록, 새 프로젝트(브리프 입력), 샘플로 시작
- 세션 화면: Conductor 대화, 전문가 실행과 진행 표시, 결과 문서 보기(Markdown 렌더링)
- state 갱신: 변경 내용을 보여 주고 적용/건너뛰기
- 옆 패널: 전문가 목록과 상태, `project_state.md`, 브리프
- 브리프와 state 편집
- 설정: 실행 모드, 프로필, RAG, API 키, 언어
- CLI는 유지합니다. 자동화, 프롬프트 실험, 테스트에 씁니다.

서버는 세 층으로 나눕니다. 나중에 화면 일부나 전체를 React로 바꾸더라도 3번만 교체하면 되게 하기 위해서입니다.

1. 코어 함수: 화면과 무관한 로직 (1단계에서 만드는 것)
2. JSON API(`/api/...`): 코어 함수를 호출해 데이터를 돌려줌. 테스트는 주로 여기에 붙입니다.
3. HTML 화면: 같은 코어 함수를 호출해 화면을 그림. 로직을 템플릿이나 화면 경로에 넣지 않습니다.

### 대지 사실 (주소 기반 법규 자료) — 진행 중

주소를 넣으면 정부 데이터에서 대지의 사실을 가져와 전문가에게 줍니다. 모델 기억이 아니라 데이터로 용도지역과 수치를 넣기 위한 것입니다. 웹 UI 2단계와 나란히 진행합니다.

정부 API는 Sida가 직접 호출합니다. 주제로 관련 조문을 찾는 일도 법제처 검색을 직접 호출하므로 별도 서버가 필요 없습니다. 법령 검색을 꺼도 이 기능은 동작합니다.

| 번호 | 내용 | 상태 |
|---|---|---|
| 1 | 주소 → 필지(여러 필지 병합 포함) → 용도지역·지구, 토지 특성, 건폐율·용적률 법정 범위 (브이월드) | 완료 (#13) |
| 2 | 행위제한(계획 용도의 건축 가능 여부), 근거 조문 목록, 기존 건축물 (공공데이터포털) | 남음 |
| 3 | 지자체 조례의 건폐율·용적률 (법제처 자치법규) | 완료 |
| 4 | 웹 UI: 주소 검색과 대지 사실의 JSON API, 새 프로젝트의 주소 칸, 대지 사실 패널 | JSON API 완료([site-ordinance.md](site-ordinance.md)), 화면 남음 |

3번이 하는 일:

- 전국 지자체가 대상입니다. 주소에서 조례를 정하는 지자체를 가려내고(구와 광역시의 군은 제외, 제주는 도), 그 도시·군계획 조례를 찾습니다.
- 건폐율 조문과 용적률 조문을 원문 그대로 저장합니다.
- 대지의 용도지역에 해당하는 줄에서 수치를 정해진 규칙으로 읽어 원문 줄과 나란히 보여 줍니다("100분의 70" → 70%, "1천300퍼센트" → 1,300%).
- 한 가지 수치로 읽히지 않거나 법정 범위를 벗어나면 수치를 내지 않고 원문만 보여 줍니다.
- 조문이 "별표와 같다"고 하면 별표 파일(HWP)을 받아 같은 방식으로 읽습니다.

3번에서 남은 것:

- 기본 수치 외의 조문(완화·강화, 용도지구)은 원문을 전부 가져와 세 묶음으로 나눕니다: 대지 위치로 정해지는 것, 설계 내용으로 얻을 수 있는 완화, 행정이 따로 지정하는 것. 설계자가 필요 없는 조문을 숨길 수 있습니다. 화면이 붙을 JSON API와 명세는 [site-ordinance.md](site-ordinance.md)에 있습니다. 이 조문들의 수치는 아직 읽지 않고 원문으로 보여 줍니다.
- 지구단위계획: 조례보다 우선할 수 있지만 법제처에 없는 자료입니다. 구역 여부만 표시합니다.
- HWPX·PDF로 된 별표.
- **소수점 조례 수치(2026-10-08):** `62.5퍼센트`를 5%로, `100분의 62.5`를 62%로 읽던 문제를 막았습니다. 소수 수치를 만나면 수치를 내지 않고 원문 줄만 보여 줍니다(`60.0`처럼 소수 부분이 0이면 60으로 읽음). 소수 수치 자체를 읽는 것은 하지 않았습니다. 지자체 30곳의 기본 조문과 별표에서는 소수 표기가 없었습니다. 실제 조문이나 별표에서 발견하면 원문을 확보하고 재현 테스트를 추가한 뒤 읽도록 넓힙니다.
- 전남광주통합특별시: 지금은 옛 광주광역시 조례를 씁니다. 통합 조례가 생기면 고칩니다.

#### 바로 이어서 할 것 (2026-10-06 기준)

대지를 고르는 방법을 넓힙니다. 서버의 JSON API와 테스트, 화면 연결 문서까지가 범위이고 화면은 팀원이 붙입니다. 필요한 정부 API는 지금 쓰는 브이월드 키로 모두 호출해 확인했습니다.

**① 단계별 선택 API** — 다음 작업

주소를 글자로 치는 대신 시·도 → 시·군·구 → 읍·면·동(→ 리) 순서로 고르고, 지번 숫자만 직접 입력합니다. 화면에서는 이 방식을 기본 입력으로 두고, 글자 검색은 주소를 붙여넣을 때 쓰는 보조로 둡니다.

| API | 동작 | 확인한 것 |
|---|---|---|
| 시·도 목록 | 17개. 코드에 넣어 둠 | |
| 시·군·구 목록 | 고른 시·도의 것 | 브이월드 데이터 API `LT_C_ADSIGG_INFO`, `sig_cd:like:41` → 47개 |
| 읍·면·동 목록 | 고른 시·군·구의 것 | `LT_C_ADEMD_INFO`, `emd_cd:like:41410` → 9개 |
| 리 목록 | 읍·면 지역만 | `LT_C_ADRI_INFO`, `li_cd:like:41830` → 110개 |
| 지번으로 필지 찾기 | 동 코드 + 본번(+ 부번, 산 여부) → 필지 후보 | `LP_PA_CBND_BUBUN`, `pnu:=:…`. 본번만 주면 `pnu:like:…`로 그 번지 전부(금정동 689 → 40개) |

- 필지 번호(PNU)는 동 코드 10자리 + 산 여부 1자리(일반 1, 산 2) + 본번 4자리 + 부번 4자리입니다. 동을 목록에서 고르면 검색 없이 조립할 수 있습니다.
- 동 이름 오타, 전국에 여러 곳 있는 같은 이름의 동, 산 번지를 글자 검색보다 정확하게 처리합니다.
- 목록은 한 번 받으면 서버가 기억해 두고 다시 부르지 않습니다.
- "조회해 저장" API(`PUT /api/projects/{name}/site`)가 지금은 검색어와 필지 번호를 받아 다시 검색합니다. 필지 번호만으로도 받도록 고쳐야 합니다.

**② 지도 API** — 그다음

주소를 찾으면 지도와 지적도가 보이고, 지도에서 필지를 클릭해 고르거나 여러 필지를 합칠 수 있게 합니다.

| 필요한 것 | 방법 | 확인한 것 |
|---|---|---|
| 배경 지도 | 브이월드 지도 타일(WMTS). 브라우저가 직접 부름 | 받아짐. 주소 검사 없음 |
| 지적도 선 | 연속지적도 레이어(WMS `lp_pa_cbnd_bubun`). 브라우저가 직접 부름 | 받아짐. `localhost`면 포트와 무관 |
| 선택한 필지의 경계 도형 | 서버 API: 필지 번호 → 도형 | `LP_PA_CBND_BUBUN`에서 다각형 좌표를 받음 |
| 지도 클릭으로 필지 고르기 | 서버 API: 좌표 → 필지 번호, 지번, 도형 | 같은 레이어의 좌표 조회 |

- 경계 도형은 조회할 때 받아 `site_facts.json`에 저장해, 다시 열 때 정부 API를 부르지 않게 합니다.
- 화면은 Leaflet이나 OpenLayers를 스크립트로 불러 씁니다. 빌드 과정이 필요 없습니다.
- 지도 타일 주소에 브이월드 키가 들어가 브라우저에 보입니다. 자기 PC에서만 도는 지금은 괜찮고, 여러 사람이 접속하는 형태로 바꾸면 서버가 지도를 대신 받아 전달해야 합니다.

**그 뒤**: 대지 사실 2번(행위제한, 근거 조문, 건축물대장).

### Rhino 연결 안정화 — 후속 작업으로 보류 (2026-10-03)

- 자동 설치 경로 탐색 중 폴더 접근 권한이 없으면 `PermissionError`로 중단됩니다. 읽을 수 없는 경로를 처리하고, 연결 불가 이유를 사용자에게 안내해야 합니다.
- `test_resolve_mcp_command_finds_router_or_none`이 실제 PC의 Rhino 설치 폴더를 탐색합니다. 임시 설치 폴더로 격리하고, 미설치·접근 거부·여러 버전이 설치된 경우를 검증해야 합니다.
- 저장 안정성과 코어 오류 처리 분리를 먼저 진행하고, 이 Rhino 수정은 별도 작업으로 진행합니다.

### 4. 전문가 구성 다듬기

- `constraint_mapper`와 `synthesizer`, `design_critic`의 겹치는 역할 정리
- 근거 자료 넓히기: 지금은 `regulation_checker`만 RAG를 씁니다. 사이트 자료(지도, 사진)와 선례 자료를 넣는 방법을 정합니다.
- 환경(일조, 바람, 소음) 렌즈를 따로 둘지 결정
- 로컬 모델에서 여러 출력을 읽는 전문가(`synthesizer`, `design_critic`)만 클라우드로 보내는 설정
- 실제 설계자의 사용 피드백으로 프롬프트 다듬기

### 5. 모델 선택 근거 만들기

- 벤치마크 스크립트: 후보 모델마다 고정 질문을 돌려 action 블록 준수율, JSON 유효율, 필수 헤더 누락률, 한국어 지시 준수율을 자동 채점
- 결과 표를 `docs/gpu_tiers.md`에 넣고 프로필 기본 모델의 근거로 사용
- 8GB GPU에서 `local` 프로필을 12K 컨텍스트로 올려도 되는지 실제 장비로 확인
- Conductor에 보내는 state에서도 안내 주석을 뺄지 실제 모델로 확인

### 6. 배포 방식 결정

- 정부 API 키를 사용자에게 어떻게 제공할지: 지금은 팀에서 키(브이월드, 공공데이터포털, 법제처)를 직접 나눠 주는 방식입니다. 사용자가 늘면 각자 발급하게 할지, 서버를 거치게 할지 정합니다.
- 설치: 지금은 Python 설치와 `run.bat`이 필요합니다. 설치 파일로 묶을지 결정합니다.
- 호스팅 서비스는 계획에 없습니다. 로컬 모델과 Rhino 연결을 쓰려면 로컬 실행이 맞습니다.

### 웹 UI 기술

**FastAPI + 서버가 그려 주는 HTML(HTMX)** 로 정했습니다(2026-10-01).

- Node 빌드 과정이 없고 Python 의존성만 늘어납니다. `run.bat`으로 그대로 실행됩니다.
- 화면의 동작이 HTTP 요청과 응답이라, 브라우저 없이 pytest로 테스트할 수 있습니다. 승인 없이 CI만으로 머지하는 이 저장소에 맞습니다.
- 화면이 평범한 HTML과 CSS라 어떤 에이전트로도 고치기 쉽습니다.
- 단점: 화면을 직접 만들어야 해서 NiceGUI 같은 완성형 도구보다 초기 작업이 많습니다.

NiceGUI는 Python만으로 빠르게 만들 수 있지만 화면 동작을 테스트하기 어렵고 라이브러리 구조에 묶입니다. React는 빌드 도구와 프론트엔드 코드가 따로 생겨서 지금 팀 규모에는 과합니다.

React가 필요해지는 시점은 서버에 다녀오지 않고 브라우저 안에서 즉시 반응해야 하는 화면이 생길 때입니다. 예를 들어 도면이나 이미지 위에 주석 달기, 전문가 관계를 그래프로 조작하기, 되돌리기와 여러 탭이 있는 편집기입니다. 지금 계획된 화면(대화, 문서, 승인, 설정, 법령 검색)에는 해당하지 않습니다. 필요해지면 그 화면만 React로 만들어 JSON API에 붙일 수 있습니다.
